## 先看结论

这批订单的 Expired 回报集中在 **10 月 27 日 00:23:00—00:23:04**，与市场结算、关闭的时间高度接近。本地适配器确实会把交易所的 `CANCELED_MARKET_RESOLVED` 状态转换为 `Expired`，因此“市场结算后批量清理挂单”是很有依据的解释。

但截图没有交易所原始状态和订单 expiration 字段，所以还不能逐笔断言 Expired 的原因。Expired 本身也不能证明订单此前完全没有部分成交。

不能把整个过程写成确定的“Oracle settle → Gamma 指挥 CLOB 关闭”。Gamma、订单回报、公开市场广播是不同接口的观测结果；现有数据不足以证明内部服务的调用顺序。

## 一、从提案到兑付，实际有哪些步骤

| 阶段 | 发生什么 | 是否已经在链上 | 与交易、兑付的关系 |
|---|---|---|---|
| Propose | proposer 提交候选结果，并按对应合约要求提供保证金、满足权限条件 | 是，提案就是链上交易 | 候选结果尚未最终确定；提案不必然触发停盘 |
| 挑战窗口 | 允许对提案提出争议；有争议时进入对应版本的复核、重新提案或裁决流程 | 争议操作在链上 | 不能只凭出现 propose 就认定可以兑付 |
| Oracle settle | 满足该请求的结算条件后，调用方提交交易，将 Oracle 答案确定下来 | 是，不是先在线下检查、再另行“上链” | Oracle 确定答案，与 CTF 已登记兑付比例是两个不同状态 |
| 结果传递至 CTF | 适配合约把最终答案转换为 outcome 的兑付比例，登记到 Conditional Token Framework | 是 | **CTF 的兑付比例登记成功后，才具备按结果 redeem 的条件** |
| CLOB 停止交易、处理挂单 | 交易服务停止接受或撮合该市场订单，处理存量挂单，发送状态回报 | 主要是链下服务状态 | 这是用户关心的“还能不能发单、take、挂着等成交” |
| Gamma 更新状态 | API/索引展示 closed、resolved 等状态 | 链下索引状态 | 是观察市场状态的窗口，不能据此证明它是撮合系统的控制器 |
| Redeem | 持仓人提交兑付交易，消耗对应仓位，领取按兑付比例计算的抵押资产 | 是 | 结果已定后，兑付仍是另一个操作，不等于每个持有人已经收到钱 |

CTF 可以理解为“记录仓位及最终兑付比例的合约”。普通二元结果下，赢家每份对应 1 单位抵押资产，输家对应 0；不是结算那一刻所有输家 token 都自动从钱包删除。

这批市场标记为 `negRisk: true`，具体资金及结果传递可能经过 NegRisk 相关适配合约。因此这里描述的是逻辑步骤，不把某一个普通二元适配器的调用路径直接套到这批市场上。

Oracle settle 与向 CTF 写入兑付比例，**可以被某个适配器组合在同一笔交易中，也可能由不同调用完成**。确认本批市场究竟是哪一种，需要检查实际交易回执及调用记录。不能用“可能隔几秒到几分钟”充当已经测到的延迟。

## 二、你贴出的 Managed Oracle 说法，哪些尚不能直接采用

“白名单 propose、15 分钟挑战期、onlyResolver settle、名义到期后仍可 dispute”都需要对应到**实际部署合约和该请求的参数**。当前材料尚未完成这项核验，所以不能认定它们就是这批天气 condition 的事实。

即使某版本源码支持这些行为，也还需要证明这批请求使用该版本。公开通用说明的挑战期，同样不能替代本次请求的实际 liveness。没有提案时间和请求参数，不能从关市时间倒减 15 分钟推算 propose。

“谁都能 dispute”也不等于没有条件：还须满足对应合约的状态、保证金等要求。

## 五、到底何时不能发单、不能 take、清空挂单

现有记录可以确认：市场在 endDate 之后还有成交；订单终止回报集中发生于 00:23 左右；公开 resolved 广播比部分订单终止回报更晚。

**现有记录不能给出精确到毫秒的统一交易截止点。** 停止接单、停止撮合、逐笔订单终止通知和各 API 状态更新，不一定同时完成。Gamma closedTime 也不是交易所最后一次成功接单或撮合的直接证据。

要把截止点继续缩小，需要当时的 CLOB 原始接受/拒绝回报、订单原始状态，以及最后成交与市场状态变化的完整记录。当前文档没有把这些缺失记录当作已经取得。

实际理解可以用下面这条流程，但右侧服务更新不应理解为已经证实的固定先后顺序：

```text
天气事实使策略认为某桶不可能发生
    ↓（与平台何时提案是两回事）
链上提出候选结果 → 挑战/争议流程 → Oracle 最终答案
    ↓
适配合约将结果传至 CTF，登记兑付比例 → 持有人可以发起 redeem

结算相关状态同时被平台服务处理：
    CLOB 停盘/终止挂单、Gamma 更新、公开市场广播
    三者的外部可见时间可以不同，不能仅凭时间顺序推导内部依赖。
```
